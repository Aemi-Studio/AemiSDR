# Diary — 2026-10-20 (02)

## The iPhone Duo's corner radii, and what reads them

The owner asked which private API gives the corner radii for the iPhone Duo, and pointed at
`Xcode_27.2_Release_Candidate.xip`. Expanded to `/Applications/Xcode_27.2_RC.app` (Xcode 27.2, 27B48; 3.7 GB, side by side with
Xcode 27.0; `xcode-select` unchanged). The iOS 27.2 simulator runtimes (24B114 and an `iOS-27-2-iPhone19-4` one, 24B91014)
and an `iPhone Duo` device then appeared on the machine; the 27.0 runtime was replaced. All Duo runtime numbers below are
from that device, run with `xcrun simctl` (default Xcode 27.0 tooling), a throwaway Objective-C app
(`/tmp/cornerapp/main.m`, built with `-mios-simulator-version-min=18.0`, one scene) and `log stream`.

| Claim | Probe | Verdict |
|---|---|---|
| An "iPhone Duo" exists in the iOS 27.0 SDK/runtime | `simctl list devicetypes` (129 types), runtime scan of 38,322 classes for hinge/fold/duo | **REFUTED** under Xcode 27.0 and the 27.0 runtime |
| It exists in Xcode 27.2 | `xcrun simctl list devicetypes` with `DEVELOPER_DIR`=27.2 | **CONFIRMED**: `iPhone Duo`, `com.apple.CoreSimulator.SimDeviceType.iPhone-Duo`, model `iPhone19,4`, product class V68, min runtime 27.1 |
| Its display geometry | `capabilities.plist` in `/Library/Developer/CoreSimulator/Profiles/DeviceTypes/iPhone Duo.simdevicetype` | two integrated displays: primary 1398×2034 @3x (466×678 pt), inner 2007×2853 @3x; `DeviceCornerRadius` 59 |

| A per-corner source exists | same app: `windowScene._FBSScene.settings.cornerRadiusConfiguration` (`BSCornerRadiusConfiguration`, image `BaseBoard`; `topLeft`, `topRight`, `bottomLeft`, `bottomRight`: `d16@0:8`) | **CONFIRMED**: Duo **tl 8, tr 59, bl 8, br 59** (matches the profile exactly); iPhone 18 Pro and Air 62 on all four |

| New public API for the hinge | diff of UIKit headers 27.0 vs 27.2 | `UIHinge` (`status`, `angle`), `UIHingeInteraction`, `UIViewReservedRegion` (occlusion / division kinds), arrangement classes; all `API_AVAILABLE(ios(27.1))`. **No public corner API.** Reserved regions on the Duo's scene: 0 occlusion, 0 division |
| The display-shape family is open to multi-rect shapes | runtime class scan | only `UISDisplaySingleRectShape` under `UISDisplayShape` (`<_UIDisplayInfoShape>` protocol: `displayShapeName`); nothing multi-rect yet |

**Not explained, recorded as open.** On the first launch after the Duo's first boot the same app saw a 386×678 pt scene, top
safe-area inset 16 and **tr/br = 30** (`cornerRadiusConfiguration` 8/30/8/30); every later launch (five) saw 466×678 and
8/59/8/59. The cause is unknown (first-boot state or a transient layout). The code reads the configuration each time rather
than caching, so it follows the system either way.

**Owed.** The inner 2007×2853 display (profile: 55 on all four): the simulator exposed only the primary display to the app.
Corner values after rotation to landscape (which corners map to which): no way to rotate was available from `simctl`; the
code documents corners as physical, as reported, and does not remap. A physical device. Whether `DeviceCornerRadius`
(MobileGestalt) is the maximum of the corners: it is 59 in the profile and read 62 on the 18 Pro (all four 62); consistent,
not proven.

## What shipped for it

`DisplayCornerRadii` (public, per corner) and `UIScreen.displayCornerRadii`; the scalar `displayCornerRadius` is now the
largest corner. Source order: scene per-corner configuration, trait scalar, screen scalar, idiom estimate. ADR-0005.
103 tests pass on the Duo (iOS 27.2) and the iOS 18.6 simulator, 91 on macOS. A live test builds the real
`BSCornerRadiusConfiguration` through Abysm with four distinct values (1, 2, 3, 4 passed as TL, BL, BR, TR) and reads it back
through the production code; making `topRight` use the `bottomLeft` getter failed two tests.

## `systemStyle`: what the probes said (fix owed)

| Claim | Probe | Verdict |
|---|---|---|
| `settingsForStyle:` could represent every style with the right ABI | scanned constants −1…4000 and 10000…11000 on iOS 27.2 | **REFUTED**: 19 distinct settings classes exist (Light 0, Dark 1, Blur 2, 20xx, 39xx, 4000…); the other 5,062 values give the UltraLight fallback. `UIBlurEffectStyle` raw values (extraLight 0, light 1, dark 2, regular 4 … systemChrome 10) are not these constants |
| `UIBlurEffect.effectSettings` is the right source | read it for each style | classic styles correct (0 → UltraLight 20 / 1.8, 1 → Light 30 / 1.8, 2 → Dark 20 / 1.8); styles 4…10 → `_UIBackdropViewSettingsNone`, radius 0 |
| The live effect view carries the real values | `UIVisualEffectView(effect:)` + `layoutIfNeeded`, read the `_UIVisualEffectBackdropView` filters | **CONFIRMED, and different per style**: regular 30 / 1.8, prominent 20 / 1.8, ultraThin 22.5 / 1.1, thin 29.5 / 1.35, material 29.5 / 1.5, thick 45 / 1.5, chrome 22.5 / 1.1 (the system materials add `luminanceCurveMap` and `colorBrightness` filters) |

So every modern preset today is the UltraLight fallback (20 / 1.8): radius off by up to 2.25× (thick: 45 vs 20) and
saturation by up to 1.6× (ultraThin: 1.1 vs 1.8). The fix is to measure the live effect view, which needs the main actor and
changes public API (`@MainActor` presets). Not done; roadmap 0002 carries the design.

## Challenged and still unprobed (found by reading)

Capture-slot reuse and pool thrash (0004), display link outliving its coordinator, `nextDrawable()` on main, render per
layout (0005), the capture signature ignoring the lens frame (0006), filter reinstall per layout (0008). Each needs a
simulator test with a seam that does not exist yet; none is claimed confirmed. The display-link fix is one line and is
still not applied for want of a test that can observe invalidation without relaxing access control.

## Mistakes of mine

- `export DEVELOPER_DIR` outlived its command, so a verification ran on Xcode 27.2 RC without my saying so; noticed from
  `swift --version` and unset. Later verifications used the default Xcode (27.0) and are labelled.
- A mutant restore with `git checkout` on an untracked file silently did nothing and left a mutation in the source; caught by
  grepping for it, restored from a backup copy, re-run.
- The first corner probe app crashed at launch: iOS 27 requires the scene lifecycle. And a long `NSLog` was truncated by the
  log system, so the probe now logs one fact per line.
- The disk fell to 2.1 GB during the work (Xcode 27.2, parallel builds by other processes, my own derived data), which made
  one `xcodebuild` fail with "unable to write file". All my build output was deleted afterwards.
