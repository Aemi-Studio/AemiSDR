# Diary — 2026-11-28 (01)

## Luma behind a view (ADR-0010); filters on iOS; the dynamic range before a blur

Probes on macOS 27.2.1 (Swift 6.4.2) and the iOS 27.2 simulator (iPhone 18 Pro). Windows were put on screen for a few
seconds with the owner's agreement.

| Claim | Probe | Verdict |
|---|---|---|
| `CABackdropLayer` tracks luma on macOS | `tracksLuma` on a plain backdrop over a window recoloured white, black, grey | refuted as set up so: one report when tracking starts, then none |
| The system's own backdrops track luma in a plain window | AppKit's scroll pocket under a toolbar, SwiftUI's glass button; their `didChangeLuma` swizzled to log | refuted: `tracksLuma` off on all of them there; turned on on SwiftUI's glass backdrop, one report, then none |
| How UIKit sets one up | `otool -tV` of the iOS 18.6 simulator's UIKitCore, `_UILumaTrackingBackdropView` | capture-only, scale 0.5, hidden while paused, `tracksLuma` when unpaused; `_UILumaTrackingGroup` adds transition boundaries, a minimum difference, outliers |
| When the renderer samples | `dyld_info -disassemble` of macOS QuartzCore, `update_backdrop_luma` | for backdrops it rendered in a group, once their interval has passed; sent by mach message 0x9dd9 |
| A setup that reports continuously | enabled + `windowServerAware` + `groupName` + scale 0.5 + `allowsFilteredLuma` + a filter, then each removed in turn | holds with all of them (white 1.00, black 0.00, #808080 0.50, #bcbcbc 0.73, every interval); without any one, it stalls; with no filter it lags |
| It can be invisible | opacity 0.01, 0.001, 0; hidden with `tracksLumaWhileHidden`; capture-only | 0.01 holds; the others report nothing |
| What the value is | sRGB red, green, blue behind it | 0.344, 0.828, 0.0625: Rec. 709 weights on the display's (P3) gamma-encoded values; 64 steps |
| It includes the window's own layers | a white layer of the window under it, a black window behind | holds: 0.95 to 0.98 |
| `lumaUpdateRate` and `lumaSubrect` | rates 0.1 to 10; a half-white window under half of it | the rate is seconds between readings; the subrect is in the layer's points (a unit rect is not) |
| The same setup on iOS 27.2 | the setters' encodings; a SwiftUI app in the simulator (a package's tests have no window scene: 0 connected scenes) | holds: same encodings but `setWindowServerAware:` (absent); readings 1.00, 0.00, 1.00 |
| `BlurFilterFactory` works on iOS | the filters made in the iOS test host | refuted: `-[CAFilter inputKeys]` does not exist on iOS, so no filter was ever made there and every blur fell back to the material. `-CAMLTypeForKey:` (`@24@0:8@16`) names each key's type and nothing for an unknown one: now asked when `inputKeys` is absent |
| The system blurs after bringing HDR into range | the materials' filter lists | holds: `sdrNormalize` (inputs left as they are) before `gaussianBlur` in every material; the recipe now does the same unless told not to |

The live test on macOS failed one run in four at first (no reading at all). The cause was occlusion: the test window was
behind other windows, and an occluded window is not drawn. Floated, 25 runs in 25 passed. `Examples/LumaCheck` on the iOS
simulator: 6 runs in 6 passed.

Not measured: what a tracking layer costs the renderer, and readings over HDR content, across Spaces and with Reduce
Transparency.

Mutation: with the layer's opacity at 0.001 instead of 0.01, `on screen, readings follow what is behind the view` fails
(no reading), and passes again once restored.

Checks: `swift test` on macOS, 223 + 21 tests; the iOS 27.2 simulator (`xcodebuild … -scheme AemiSDR-Package`), 193
tests; `Examples/LumaCheck` on the simulator; swift-format, deadwood, dolly, arcleak clean.
